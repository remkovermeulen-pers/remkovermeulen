How to let everyone in your company prototype

In the first article of this series I argued that building is no longer the bottleneck in product management. Attention and communication are. The fastest way to communicate an idea is to show it, which makes prototyping a skill for the whole company, not only for designers and engineers.

01

Prototype on the real product, not a copy

The starting point is a playground: a separate copy of our front-end code with mock data instead of a real back end. Because prototypes use the same components and design system as the product, they look and behave like the product. Feedback from customers is about the idea, not about an unfamiliar interface. And when a prototype works, engineers start from code that already uses the right building blocks.

The mock data comes in three states, switched with a simple parameter in the URL: a workspace full of realistic data, an empty workspace and the onboarding flow. That means you can test how a feature feels for a long-time customer, for someone who has just signed up and for everything in between.

02

Make the setup a one-time step

For most people, the barrier is not prototyping itself. It is the setup: repositories, terminals, dependencies. We reduced that to a short checklist that you complete once: access to the playground on GitHub, the Claude desktop app, and a folder on your computer for the code.

The last step is a Claude skill that does the rest. You type a single command, and the skill checks what is in place, installs what is missing and tells you what still needs attention. After that, nobody needs to open a terminal again.

03

Keep the workflow in plain language

Everything after the setup is a sentence typed into Claude Code. You start each prototype with "Create a branch called Automations & Agents", using whatever name fits your idea. Then you describe what you want to build, much as you would in Claude Design, and watch the preview update next to the conversation. Typing "Commit" saves your work.

When you want feedback, you type "Commit and PR". Claude replies with a public URL that you can send to a customer, a tester or a colleague. Preview links expire two months after the last change, which keeps the number of old prototypes in check.

The terms branch, commit and pull request are still there, and people pick them up along the way. But nobody needs to understand Git before they can test an idea with a customer.

04

Protect the design system

When everyone can change the front end, the design system is at risk. A prototype that quietly changes a shared button or form field creates confusion later, when engineers have to work out which version is right.

The rule is simple: prototypes build on the existing design system but do not change its components. Instructions for Claude in the repository say so, and a check runs automatically to confirm that no design-system components were modified. When a prototype does need a new or changed component, that goes through a separate process with the design team.

05

Improve the starting point together

The playground gets better every time someone uses it. If you improve the mock data or fix an issue that would affect every prototype, you create a separate baseline branch, make the change and open a pull request. An engineer from the front-end team reviews it before it becomes part of everyone's starting point.

This keeps engineers involved where it matters, in what goes into shared code, without making them a bottleneck for every individual prototype.

06

How to set this up in your company

  1. Create a playground. Copy your front end into a separate repository and replace the back end with mock data. Add a few data states, such as a full workspace, an empty one and the onboarding flow, and make sure the playground has no access to production data or live systems.
  2. Write instructions for Claude. Add a file to the repository that tells Claude how to run the preview, which design-system components to use and what it must not change. This file does most of the work of keeping prototypes consistent.
  3. Add a design-system check. Run an automatic check that fails when a prototype changes a shared component. Instructions guide Claude; the check catches what slips through.
  4. Set up preview links. Configure your hosting so that every pull request gets its own public URL, and let previews expire after a period without changes. We use two months.
  5. Write a setup skill. One command that checks access, installs what is missing and reports what still needs doing. This turns a morning of setup into ten minutes.
  6. Arrange access. Give everyone who should prototype a GitHub account in your organisation and the Claude desktop app.
  7. Write a one-page guide and record a short video. List the handful of sentences people type, from creating a branch to getting a public link. Most people only need to see it done once.
  8. Agree who reviews the baseline. Name a front-end engineer who reviews changes to the shared starting point, and keep prototype branches free of review.
  9. Start small. Run a first session with three or four people from different teams, sit next to them while they build their first prototype, fix what confuses them, then open it up to everyone.
07

Concerns you will hear, and how to answer them

Opening up prototyping changes who does what, so expect pushback. These are the concerns that come up most, with the answers that work.

"Prototype code will end up in production." Engineers worry they will be asked to ship whatever was demoed. The answer is in the setup: the playground is a separate repository with mock data, and nothing in it is merged into the product. A prototype is a specification you can click, not a pull request. Engineers still decide how to build it properly.

"The design system will fall apart." Designers worry about dozens of slightly different buttons. The automatic check blocks changes to shared components, and anything new goes through the design team. In practice designers spend less time drawing every screen and more time reviewing prototypes and improving the system everyone builds on.

"I'm not technical enough for this." You will hear this from product managers, customer success and marketing. The setup skill, the plain-language commands and one session with someone sitting next to them usually solve it. A customer success manager who hears the same complaint from three customers can prototype a fix and show it to the next one that week.

"Public links will leak unreleased features." A fair point from security and leadership. Prototypes only use mock data, preview links are long and hard to guess, and they expire. Avoid real customer names in mock data, and keep anything truly confidential out of the playground.

"Customers will expect it next week." Sales and account managers worry about promises. Label every prototype clearly, let account managers introduce it as an experiment, and never attach a date to a prototype shown to a customer.

"Everyone will build their own pet features." Leadership worries about focus. Start each prototype from a project or problem that is already on the list. Prototyping makes testing cheaper; it does not change who sets priorities.

"Who pays for it?" Compare the cost of licences and preview hosting with one round of design and engineering time spent on an idea that customers turn out not to want. The first avoided rebuild usually pays for the year.
